# AWS implementation notes

AWS mapping for this skill's principles. As of 2026-10; services change, verify before use.

This file maps the offline suite onto Amazon Bedrock AgentCore Evaluations and the runtime's tracing. Online evaluation, dashboards and alerting belong to agent-ops-reviewer. The three evaluation modes, ground truth in batch and on-demand evaluation, the trajectory evaluators, the CloudWatch ingestion wait and the shape of batch results were checked against AWS documentation on 2026-10-11. Items marked (unverified) were seen in hands-on labs but not confirmed in the documentation.

## Built-in evaluators are generic judges

The built-in evaluators (correctness, helpfulness, coherence, faithfulness, conciseness and others) are LLM judges with general-purpose rubrics. Under this skill's rules they rank outputs for review and don't gate a release until they've been calibrated on your own labels (llm-judges.md, "Calibration protocol").

In the lab, helpfulness scored high on exactly the sessions where the agent invented an account balance. Only the reference-based correctness evaluator, given an expected response, scored them zero. Treat helpfulness and coherence as soft dimensions, and pair them with ground truth or state checks (scorers.md, "Divergence check").

## Checking that ground truth was used

Ground truth fields are optional, and evaluators fall back to their reference-free mode without them. A trace with no `expectedResponse` is scored by `Builtin.Correctness` as a reference-free judge, and nothing fails. The plain-string form of `expectedResponse` is matched to the session's last trace only, so earlier turns of a multi-turn session go reference-free unless each expected response is scoped to its trace ID. A field that an evaluator received but didn't use comes back in `ignoredReferenceInputFields`.

Before trusting a correctness score, assert per trace that an expected response scoped to that trace was sent and isn't listed as ignored. Otherwise the score came from a reference-free judge, which can't see confident wrong answers.

## Custom judges

- Pick the level first: session, trace or tool call. The instruction must use that level's placeholders. Placeholders that need ground truth are filled from the reference inputs of a batch or on-demand run. An evaluator that uses them can't be added to an online configuration, because live traffic has no ground truth.
- A template gives you a starting rubric and scale. Rewrite the scale for your dimension. A tone judge that keeps a faithfulness scale can't express a tone failure (review-checklist.md, "Judge rubric cannot express the failure").
- Choose a judge model from a different family than the agent.
- Prefer binary pass/fail criteria, and compute pass in code from per-session results.
- Before a new judge scores a batch, run it on-demand on a few known-bad sessions. If a fluent wrong answer gets the top level, fix the scale first.

## Trace-sourced batches

Batch evaluation reads sessions from the runtime's logs, so requirement 13 in datasets-and-harness.md applies in full.

- Confirm the trace destination is active before sending traffic. Spans sent earlier were rejected and lost in the lab (unverified).
- Read each invocation's response stream to the end, so the session completes and exports its spans (unverified).
- AWS documents a wait of 2 to 5 minutes for CloudWatch to ingest telemetry before evaluating. A fixed sleep shorter than that loses sessions. Poll per session until its spans are queryable, with a deadline above that window. Filter on the span stream of the runtime's log group, because other streams also contain the session ID and give false "found" results.
- If any sampling or indexing percentage applies to these traces, eval sessions need 100%. Which settings affect what batch evaluation reads is unverified.
- Log the pipeline state before traffic and again on timeout.
- After the batch, compare sessions sent with sessions scored per evaluator. Recompute the headline from per-session detail with missing = failed, and report sent, scored and errored (review-checklist.md, section 1).

## Eval-mode runtime

Batch evaluation scores sessions you generate by invoking the deployed runtime, so the agent's tools run for real. Deploy an eval endpoint or variant whose write tools hit a recorder or sandbox (datasets-and-harness.md, requirement 2), and keep everything else identical to production.

## Prompts in a config store

If the runtime reads its system prompt from a parameter store on every call, an edit made while a batch is still sending mixes two prompts in one batch. Point the runtime at a pinned parameter version or label (Parameter Store supports both), write the version into each trace, and assert one version per run before scoring (datasets-and-harness.md, requirement 6). Hot reload is fine in a dev or eval environment. In production a prompt change is a release that goes through the gate (agent-ops-reviewer).

## Reading results

- Per-session results in CloudWatch Logs are the unit for Wilson intervals, the paired sign test and the bootstrap (statistics.md). Console averages don't support any of them.
- If a past run kept only the batch summary (averages and session counts), recompute its mean with missing sessions at the scale's floor (statistics.md, "Mean scores"). That history supports no interval and no paired test.
- Trend graphs on the evaluation metrics namespace mix runs, prompts and conditions. They are not paired comparisons.
- A 10-session batch cannot support a 0.80 pass bar (statistics.md, "Worked example: a 10-session batch").
